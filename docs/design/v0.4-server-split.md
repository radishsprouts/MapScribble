## 0. 変えない決定事項（02章・依頼より）

1. 鍵は**今いるワールドのシードのハッシュ**（hashed seed）。MapModCompanion の ID は使わない
2. リフレクションを使わない（`rules/29`。テストも含む）。`compat/WorldIdentityCompat` で吸収し、公開 API で取れなければ AW（Fabric）/ AT（Forge・NeoForge）で開ける
3. 普通のサーバーとシングルの動きは今までと同じ。分けるのは「同じ接続の中でハッシュが変わるのを見たアドレス」か「利用者が分けると選んだアドレス」だけ。記録は `servers/<アドレス>/notebooks.json`
4. `servers/<アドレス>/` 直下の今までのファイルは、消さない・動かさない・名前を変えない。分けた後も全サーバーで見え、編集でき、編集は元のファイルへ書く。メモ帳が決まっていない時は直下へ書く
5. 「移す」は、移し先へ書いて読み直せたことを確かめてから元から除く。元の内容は `<名前>.before-split.bak` として1回だけ残す。元に戻すで戻せる
6. 書き込みは一時ファイル経由（`store/MemoFile.java:163-173` の `writeAtomic` のまま）。知らない形式は読まず、上書きもしない（`MemoFile.java:86-91` の UNSUPPORTED）

## 1. シードのハッシュの取り方

### 1.1 結論

- **25構成すべてで、hashed seed は公開 API では読めない。** 値は `net.minecraft.world.level.biome.BiomeManager` の `private final long biomeZoomSeed` にだけある。`BiomeManager` には値を返す公開メソッドが無い（公開の static は `obfuscateSeed(long)` だけ）。`Level.getBiomeManager()` は public
  - 確かめた jar（javap）:
    - Fabric（loom のキャッシュ `.gradle/loom-cache/minecraftMaven/net/minecraft/minecraft-merged-*`）: 26.1.2・26.2・26.3・1.20.1・1.20.6・1.21.1・1.21.4・1.21.11
    - NeoForge: `versions/*-neoforge/build/moddev/artifacts/neoforge-20.6.144.jar`・`21.1.264`・`21.4.161`・`21.11.48`、`minecraft-patched-26.1.2.122`・`26.2.0.93`・`26.3.0.97`
    - Forge: `versions/1.20.1-forge/build/moddev/artifacts/forge-1.20.1-47.4.28.jar`、`.gradle/mavenizer/repo/net/minecraftforge/forge/` の 1.20.6-50.2.14・1.21.11-61.2.4・26.1.2-64.1.5・26.2-65.1.5・26.3-66.1.0
    - 0.5.0 で足す 1.19.2・1.18.2: Mojang の client.jar と client.txt（Mojang 公式マッピング）。1.19.2 は `BiomeManager`→`chv`、`biomeZoomSeed`→`f`（private final long）。1.18.2 は `cbt`、`f`（private final long）。取った jar は scratchpad（`C:\Users\radis\AppData\Local\Temp\claude\2e91288c6ca4719e\05384311-95f8-4a68-b563-5accb7f3b487\scratchpad\mcjar\`）にあり、リポジトリには入れていない
  - 26.3 では `BiomeManager` のコンストラクタが `(BiomeResolver, long)` に変わった（他の版は `(BiomeManager$NoiseBiomeSource, long)`）が、フィールドの名前と型は全版で同じ
- **よって AW/AT が要る。** 開けるのは `BiomeManager.biomeZoomSeed` 1つだけ（読むだけなので `accessible` / `public` で足り、`mutable`・final 外しは要らない）
- ソースは全構成で同じ1行 `level.getBiomeManager().biomeZoomSeed` になる（Stonecutter の分岐は要らない）。開発時はどの構成も Mojang 名で書く

### 1.2 方式の比較

| 案 | 内容 | 採否 | 理由 |
|---|---|---|---|
| A | AW/AT で `biomeZoomSeed` を開け、ラッパーから型付きで読む | **採用** | 値そのものを、全版同じ名前・同じ1行で読める。開けるのは1メンバーだけで影響が小さい。`rules/29` が認める方法 |
| B | Mixin の `@Accessor` | 不採用 | 今の MapScribble には Mixin が無い。各ローダーで mixins.json・refmap・manifest/mods.toml の宣言と、Forge 1.20.1 の refmap の再マッピングが要り、1つのフィールドを読むために変換の仕組みを丸ごと持ち込む。壊れる箇所が増える |
| C | ログインのパケット（`ClientboundLoginPacket` / 1.20.2 以降は `CommonPlayerSpawnInfo`）を Mixin で捕まえる | 不採用 | 注入点が版ごとに違い（1.20.2 で `CommonPlayerSpawnInfo` に移った）、B と同じく Mixin の仕組みが要る。ClientLevel に入った値を読む A の方が、入口が1つで済む |
| D | 公開の `BiomeManager.withDifferentSource` と自前の NoiseBiomeSource で、シードから決まる座標のずれを測って指紋を作る | 不採用 | 値そのものではなく指紋なので衝突がありうる。ずれの算法は版で変わりうる。読んで意図が分からない |
| E | MapModCompanion の ID | 不採用（決定事項） | 02章「見分け方」2。チャネルが地図 MOD と衝突し、地図 MOD の有無で鍵が変わる |

#### 各ビルドスクリプトへの入れ方

`ROOT` は `rootProject.file(...)`（Stonecutter の各構成は `versions/<構成>/` で動くので、リポジトリ直下からの相対で指す）。

**build.fabric-remap.gradle.kts / build.fabric-unobf.gradle.kts**

1. loom の設定に AW を指す（remap は `named.accesswidener`、unobf は `official.accesswidener`）
   ```kotlin
   loom {
       accessWidenerPath = rootProject.file("src/main/accesswidener/named.accesswidener")   // unobf は official
   }
   ```
2. `tasks.processResources`（remap は `:95`、unobf は `:114`）に、同じファイルを jar の直下へ固定の名前で入れる
   ```kotlin
   from(rootProject.file("src/main/accesswidener/named.accesswidener")) {   // unobf は official
       rename { "mapscribble.accesswidener" }
   }
   ```
3. `src/main/resources/fabric.mod.json` に `"accessWidener": "mapscribble.accesswidener"` を足す（`depends` の前。今はこのキーが無い）。Forge・NeoForge のビルドは `fabric.mod.json` を除いている（`build.neoforge.gradle.kts`・`build.forge.gradle.kts`・`build.forge-fg7.gradle.kts` の processResources の `exclude`）ので影響しない
4. ビルドの後、jar の中の `mapscribble.accesswidener` の見出しが、remap 構成で `intermediary`、unobf 構成で `official` になっていることを確かめる（1.4）
5. AW の検査は loom の `validateAccessWidener` タスクで行える（`check` に含まれるかは未確認。含まれなければ CI で明示して回す）

**build.neoforge.gradle.kts**

1. `neoForge { ... }`（`:48`）に AT を指す。MDG の既定の場所（`src/main/resources/META-INF/accesstransformer.cfg`）を使わないので指定が要る
   ```kotlin
   neoForge {
       accessTransformers.from(rootProject.file("src/main/accesstransformer/mojmap.cfg"))
       validateAccessTransformers = true
   }
   ```
   （DSL の正確な書き方は MDG の README に従う。ビルドで確かめる。MDG は `validateAccessTransformers = true` を勧めている）
2. processResources（`:101`）で jar へ入れる
   ```kotlin
   from(rootProject.file("src/main/accesstransformer/mojmap.cfg")) {
       into("META-INF"); rename { "accesstransformer.cfg" }
   }
   ```
3. `src/main/resources/META-INF/neoforge.mods.toml` に宣言を足す（NeoForge は宣言の無い AT を読まない。NeoForge 26.1.2 本体の mods.toml にも `[[accessTransformers]] file="META-INF/accesstransformer.cfg"` がある）
   ```toml
   [[accessTransformers]]
   file="META-INF/accesstransformer.cfg"
   ```

1. jar には `srg.cfg` を `META-INF/accesstransformer.cfg` として入れる（processResources `:104`。書き方は NeoForge と同じ）。Forge は `META-INF/accesstransformer.cfg` を宣言なしで読む
2. 開発時（compileJava と runClient）に AT を当てる指定を `legacyForge { ... }`（`:50`）に書く。**どちらのファイルを指すかは未確認**: MDG legacy は SRG→Mojang 名の対応表を作る（LEGACY.md）が、AT の名前を変換するかは文書に無い。先に `srg.cfg` を指してビルドし、`WorldIdentityCompat` の `biomeZoomSeed` の参照がコンパイルできるかを見る。通らなければ `mojmap.cfg` を指す（jar に入れるのは常に `srg.cfg`）。どちらで通ったかを、ビルドスクリプトのコメントと記憶に残す

**build.forge-fg7.gradle.kts（Forge 1.20.6・1.21.11・26.1.2・26.2・26.3）**

1. ForgeGradle 7 の変更履歴によると、AT は `net.minecraftforge.accesstransformers` プラグインを ForgeGradle より**先に**適用し（7.0.0-beta.21）、Minecraft の依存の側で宣言する（「ATs must be declared within the Minecraft dependency itself」beta.21、「Allow AccessTransformer opt-in from minecraft extension」beta.23、`useDefaultAccessTransformer()` の別名 rc.9）。`plugins { }`（`:5`）と `minecraft { }`（`:61`）に足す。正確な DSL はビルドで確かめる

### 1.4 AT/AW が効いていない jar での安全装置と、確かめ方

- AW/AT が jar で効いていないと、実行時に `IllegalAccessError`（`LinkageError` の一種）が出る。`WorldIdentityCompat.hashedSeed` はこれを catch し、**一度だけ** warn を出して `0`（取れない）を返す。0 は「分けない・直下へ書く」（2.4）なので、効いていなくても**今までと同じ動き**に倒れる（メモは消えない・見えなくならない）。catch はリフレクションではない
- 確かめ方（構成ごと、Dev-Engineer が W1 で、統合後に Dev-QA）:
  1. ビルドが通る（コンパイル時に AW/AT が当たっていないと `biomeZoomSeed has private access` でコンパイルが止まる）
  2. jar を開いて、AW/AT のファイルの名前・見出し・中身を見る（remap 構成は `intermediary` に変わっていること、Forge 1.20.1 は `f_47863_` のままであること）
  3. 開発用クライアント（MCP の minecraft-client）で起動してシングルのワールドに入り、ログに `MapScribble: hashed seed を読めない` の warn が**出ない**ことと、デバッグログの `hashed seed=` が 0 でないことを見る。少なくとも 01章「実機で見る構成」の 26.3 Fabric・1.20.1 Forge・1.21.1 NeoForge と、未確認の Forge 1.20.6・1.21.11 は必ず起動して見る

### 1.5 ラッパー `compat/WorldIdentityCompat`（新規）

```java
package io.github.radishsprouts.mapscribble.compat;

/** ワールドの見分けに使う値を、版・ローダーの違いを隠して返す。主スレッドから呼ぶ。 */
public final class WorldIdentityCompat {
    /** ハッシュが取れない時の値。0 はサーバーがシードを隠した時にも来るので、同じに扱う。 */
    public static final long UNKNOWN = 0L;

    /**
     * そのワールドの hashed seed（BiomeManager.biomeZoomSeed。AW/AT で開けてある）。
     * level が null、または AW/AT が効いていない jar では UNKNOWN。
     */
    public static long hashedSeed(net.minecraft.world.level.Level level);

    /**
     * 今の接続の実体（netty の net.minecraft.network.Connection）。同じ接続のままかを == で比べるためだけに使う。
     * 未接続なら null。シングルでも内部の接続が返るが、呼び出し側はシングルでは使わない。
     */
    public static Object connectionToken();
}
```

- `hashedSeed` の中身は `return level.getBiomeManager().biomeZoomSeed;` と `catch (IllegalAccessError e)` だけ
- `connectionToken` は `Minecraft.getInstance().getConnection()`（`ClientPacketListener`）の `getConnection()`。26.3 では両方 public（`Minecraft.getConnection()`、`ClientCommonPacketListenerImpl.getConnection()`）。1.20.2 未満は `ClientPacketListener.getConnection()`。名前が同じなので Stonecutter の分岐は要らない見込み（全版のコンパイルで確かめる。違えばこのクラスの中だけで分岐する）
- ハッシュを読むのは **ClientLevel の実体が変わった時だけ**（2.2）。BiomeManager は ClientLevel のコンストラクタで受け取ったシードで作られ、ClientLevel が生きている間は変わらない（26.3 の `ClientPacketListener.handleLogin` が `new ClientLevel(..., CommonPlayerSpawnInfo.seed(), ...)` を作る。1.20.1 は `ClientboundLoginPacket.seed()` を渡す）

### 1.6 プロキシでのサーバー移動と ClientLevel の作り直し

| 経路 | クライアントで起きること | 根拠 |
|---|---|---|
| Velocity・1.20.2 未満のクライアント | プロキシが JoinGame（ログインのパケット）を送り直し、続けて Respawn を送る（`doFastClientServerSwitch`）。Legacy Forge では safe switch（JoinGame → 別ディメンションへ respawn → 正しい respawn） | Velocity の `ClientPlaySessionHandler`（WebFetch で読んだ） |
| 1.20.1 クライアントの handleLogin | 分岐なしに `new ClientLevel(...)` を作り、`ClientboundLoginPacket.seed()` を渡す | 1.20.1 の `ClientPacketListener.handleLogin`（javap） |
| Velocity・1.20.2 以降のクライアント | プロキシが `switchToConfigState()` で configuration 段階へ戻す。クライアントは `handleConfigurationStart` で `Minecraft.clearClientLevel(new ServerReconfigScreen(..., Connection))` を呼び、**同じ `Connection`** で `ClientConfigurationPacketListenerImpl` を作る。configuration が終わると新しい `ClientPacketListener` ができ、handleLogin で新しい ClientLevel を作る | 26.3 の `ClientPacketListener.handleConfigurationStart`・`handleLogin`（javap）、Velocity の `ClientPlaySessionHandler` |
| 同じサーバーの中でのリスポーン | 違うディメンションへの respawn だけ ClientLevel を作り直す。同じディメンションなら作り直さない | 1.20.1 `handleRespawn` の `if_acmpeq`、26.3 の `handleRespawn` |

よって、**どの版でも、プロキシの先でサーバーが変わると新しい ClientLevel（新しいハッシュ）ができ、netty の `Connection` の実体は同じまま**になる。これが 2章の判定の土台。

## 2. 切り替わりの判定

### 2.1 今の作りの問題

`StoreSession.updateDimension`（`StoreSession.java:79-95`）は `:87` で「ディメンション・接続先（`currentConnection()`）・鍵がある」を比べて弾く。`currentConnection()`（`:98-104`）は `ServerData` の実体を返すが、プロキシの先でサーバーが変わってもこの実体は同じで、ディメンションも overworld→overworld のように同じことがある。そのため切り替わりを検出できない。

### 2.2 足す比較（毎 tick の費用は参照の比較1回だけ）

`StoreSession` に次のフィールドを足す。

```java
/** 前回見た ClientLevel。実体が変わった時だけハッシュを読み直す。リークを避けるため弱参照。 */
private static WeakReference<Level> lastLevel = new WeakReference<>(null);
/** 前回読んだハッシュ（lastLevel のもの）。 */
private static long lastSeedHash = WorldIdentityCompat.UNKNOWN;
/** 切り替わりの検出器（Minecraft に依存しない。2.3）。切断では消さない。 */
private static final SplitDetector DETECTOR = new SplitDetector();
/** 利用者が今の接続の中で手で選んだメモ帳（4.5 の select(remember=false)）。ハッシュが変わったら外す。 */
private static ManualSelection manualSelection;
```

`updateDimension(dimension)` の新しい流れ（`:79-95` を置き換える）:

```
if dimension == null:
    lastDimension = null; lastConnection = null; lastLevel = 弱参照(null); manualSelection = null
    CONTROLLER.update(null, null)            // 今と同じ。DETECTOR は消さない（2.3）
    return
```

- `createKey(dimension, seedHash)` は今の `:115-136` に、マルチの時だけ `NotebookRegistry.resolve(addressDir, seedHash, manualSelection)` でメモ帳を決めて `SessionKey` に入れる処理を足す（4.4）。シングル・`saves/unknown` は今のまま（メモ帳は null）
- `SessionKey` は `record SessionKey(Path dataPath, String worldId, String dimension, String notebook)` にする。今の3引数のコンストラクタも残し（notebook = null）、今の試験（`SessionControllerTest`）を壊さない。`file()` は notebook が null なら今の `MemoFile.resolve(dataPath, dimension)`、そうでなければ `dataPath/notebook/<ファイル名>`。`legacyFile()` は notebook がある時だけ `MemoFile.resolve(dataPath, dimension)`、無ければ null
- メモ帳が変わると鍵が変わるので、`SessionController.update`（`store/SessionController.java:32-48`）がそのまま「書き切る → 捨てる → 読み直す」を行う。`started` は `store.open(key.file(), key.legacyFile())` を呼ぶ形に変える（`:56`）

### 2.3 「同じ接続の中でハッシュが変わった」の判定（`store/SplitDetector`、新規・Minecraft 非依存）

```java
/** 1つの接続の中で、同じディメンションIDのハッシュが変わったかを見る。主スレッドから使う。 */
public final class SplitDetector {
    /** 判定の結果。split が true の時、previous は同じディメンションIDで前に見たハッシュ。 */
    public record Result(boolean split, long previous, long current) { }

    /**
     * ClientLevel が変わった時に1回呼ぶ。
     * @param connection 接続の実体（WorldIdentityCompat.connectionToken()）。null なら何もせず split=false
     * @param dimensionId 例 "minecraft:overworld"
     * @param seedHash UNKNOWN(0) なら何も記録せず split=false
     */
    public Result observe(Object connection, String dimensionId, long seedHash);
}
```

- 内部に「接続の実体（`WeakReference`）」と「その接続の中で、ディメンションIDごとに最初に見たハッシュ（`Map<String, Long>`）」を持つ
- `connection` が前と違う実体（または前の実体が回収された）なら、表を空にして記録し直す。**切断（`updateDimension(null)`）では消さない**: Fabric の `ClientPlayConnectionEvents.DISCONNECT`（`MapScribble.java:108`）が configuration への移行の時に呼ばれるかは未確認だが、表を `Connection` の実体で持つので、呼ばれても呼ばれなくても同じ結果になる
- **split と判定する条件**: 同じ接続の実体で、同じディメンションIDについて、0 でないハッシュを前に見ていて、今のハッシュが 0 でなく、前と違う
  - ディメンションIDまで見る理由: 普通のサーバーで、Multiverse 等で別のワールド（別のディメンションID）に別のシードがある時に、誤って分けないため（決定事項 3「普通のサーバーの動きは今までと同じ」）。ディメンションIDを見ない案は、このサーバーを誤ってプロキシと見なすので不採用
  - 「前に見た」は直前ではなく、**その接続で最初に見た値**と比べる。プロキシで lobby（overworld）→ survival のネザーで出現 → survival の overworld、と移った時にも、overworld 同士で比べて拾える
- 判定は記録するだけで、メモの読み書きはしない（試験しやすくするため）

### 2.4 ハッシュが 0・取れない時

- `UNKNOWN`（0）は「取れない」として扱う。`SplitDetector` は記録しない（0 を挟んでも、0 でない値同士で比べる）
- `NotebookRegistry.resolve` は、ハッシュが 0 の時はメモ帳を選ばない（直下へ書く）。分けると記録したアドレスでも同じ（02章「見分け方」3）。利用者が手で選んだメモ帳（4.5）だけは使う
- AW/AT が効かない jar も 0 になり、今までと同じ動きになる（1.4）

### 2.5 notebooks.json に「分ける」を記録する流れ

`onLevelChanged(dimension, seedHash)`（StoreSession の private）:

1. シングル、または接続先のアドレスが無いなら何もしない
2. `Result r = DETECTOR.observe(WorldIdentityCompat.connectionToken(), dimId, seedHash)`
3. `manualSelection` が別のハッシュのものなら外す
4. `r.split()` が false なら終わり
5. `NotebookRegistry` でそのアドレスの状態を見る（主スレッドで読む。4.2。結果はアドレスごとにメモリへ持つので、読むのは最初の1回だけ）
   - 読めない（CORRUPT・UNSUPPORTED）: 何も記録しない。直下へ書き続ける。問題の受け手（`StoreSession.addNotifier`）へ1回だけ知らせる（「保存先の記録ファイルを読めなかったため、サーバーごとに分けずに保存します」）
   - `mode` が `off`（利用者が分けないと選んだ）: 何もしない
   - `mode` が `auto` か `user`（もう分けている）: 何もしない（resolve が自動で選ぶ）
   - 記録が無い: 次へ
6. **書いてから使う**: 新しい内容（`mode = auto`、`splitAt = 今`、`r.previous()` と `r.current()` それぞれに `nb-<16進>` のメモ帳を作って `bindings` に入れる）を、書き込み用スレッドで `notebooks.json` へ書かせ（4.2）、書いて読み直せたら主スレッドで `NotebookRegistry` のメモリ上の状態を差し替えて、`CONTROLLER.update(createKey(...))` で鍵を作り直す（ここで初めてメモ帳へ切り替わる）
   - 書けなかったら、メモリ上も分けないまま（直下へ書く）にし、問題の受け手へ知らせる。**記録が残らないまま新しいメモ帳へ書くと、次に入った時にそのメモが見えなくなるため**（01章 2「見えなくしない」）
7. 説明の行（「このアドレスは中で複数のサーバーに分かれているので、サーバーごとにメモ帳を分けました」）を出すための通知を、新しい受け手 `StoreSession.addNotebookListener(Runnable)` へ送る。文言と出し方は Dev-UI-Designer

- 前のサーバー（`r.previous()`）で、分ける前に描いたメモは直下に残る。分けた後も直下のメモは全サーバーで見える（3章）ので、消えたようには見えない
- 分けた後に、新しいハッシュを見たら（3つ目のサーバー、資源ワールドのリセット）、`resolve` がそのハッシュの `nb-<16進>` を作って `bindings` に足す（4.4）。この書き込みも 6 と同じ「書いてから使う」

### 2.6 リスク: 入るたびにハッシュを変えるサーバー

- シードを隠すために、ログインのたびに乱数のハッシュを送るサーバー（プラグイン）があると、同じ接続の中でネザーから戻った時に overworld のハッシュが変わり、2.3 の条件に当たって分けてしまう。その後は入るたびに新しいメモ帳になり、前のメモ帳のメモが見えにくくなる（フォルダは残り、保存先の画面で選べる。直下のメモは常に見える）。こうしたサーバーが実在するかは**未確認**
- 緩和（この版で入れる）: `mode = auto` のアドレスで、同じディメンションIDに紐付いたハッシュが **8 個**を超えたら、そのアドレスの自動の作成を止める（`autoStopped = true` を記録し、以後は直下へ書き、問題の受け手へ「このサーバーは入るたびにシードが変わるため、自動で分けるのを止めました」と知らせる）。利用者は保存先の画面で `mode` を `user` か `off` に変えられる
- 8 という数は、プロキシの下のサーバーの数（ふつう数個）より大きく、乱数のサーバーなら数回の出入りで超える値として置いた。変えるなら `NotebookRegistry.AUTO_LIMIT` の1か所

## 3. 2ファイルを同時に開く作り

### 3.1 MemoStore の持ち物（`store/MemoStore.java` を作り替える）

今は1ファイル（`file`・`writable`・`memos`・`view`、`MemoStore.java:26-31`）。これを次にする。

```java
/** 1つのファイルとその中身。 */
private static final class Slot {
    final Path file;
    final boolean writable;          // MISSING か OK の時だけ true（MemoFile.ReadResult.canWrite）
    final List<Memo> memos;          // 変更できる一覧
}
private Slot primary;                // 書き込み先。null なら使えない
private Slot legacy;                 // 分ける前のファイル。メモ帳を開いた時だけ。読めなかった時は null（触らない）
private final Map<UUID, Slot> origin = new HashMap<>();             // 見えているメモの元のファイル
private final LinkedHashMap<UUID, Slot> removedOrigin;              // 消したメモの元のファイル（上限 256、古い順に捨てる）
```

### 3.2 開く・閉じる

- `open(Path primaryFile, Path legacyFile)`（新規）。今の `open(Path)`（`:125-139`）は `open(file, null)` を呼ぶだけにする
  1. `discardCurrent()`（今のまま。予約分を書き切ってから捨てる、`:157-163`）
  2. 主ファイルを `MemoFile.read`。今と同じく、書けなければ `problemHandler` に知らせる（`:132-137`）
  3. `legacyFile` が null でなく主ファイルと別のパスなら読む
     - MISSING・OK: `legacy = Slot(writable = true)`
     - CORRUPT・UNSUPPORTED: **`legacy = null`（表示しない・触らない）**。`problemHandler` に「分ける前のメモのファイルを読めなかったため表示できません（ファイル名）: 理由。ファイルには触りません」を知らせ、warn を出す
  4. `origin` と `removedOrigin` を作り直し、`generation++`、`refreshView()`、`notifyListeners()`
- `close()` も `generation++`
- 試験用に `open(Path)` の今の動きは一字も変えない（`MemoStoreTest` がそのまま通ること）

### 3.3 表示の一覧（view）

- 順序: **分ける前のメモ（legacy）を先、主ファイルのメモを後**（後ろほど上に描く。`MemoRepository.java:203` の約束どおり、新しいメモ帳のメモが上に来る）
- **同じ id が両方にある時**（移す操作の途中で落ちた等）は、主ファイルの方だけを出し、legacy の方は出さず触らない（`origin` は主ファイル）
- 描画（`MapCanvasRenderer`）・当たり判定（`draw/HitTester`）・ミニマップの同期（`jm/ScribbleBridge.java:703-734`）は `repo.memos()` だけを見ているので、**変更は要らない**。両方のファイルのメモがそのまま描かれ、消しゴム・編集の対象になる

### 3.4 追加・変更・削除の行き先

| 操作 | 行き先 |
|---|---|
| `add(memo)` | `removedOrigin` にその id があれば（＝削除の取り消し）その元のファイルへ戻す（そのファイルが今開いていて書ける時）。無ければ主ファイル |
| `update(memo)` | `origin.get(id)` のファイル。今のまま、無ければ何もしない |
| `remove(id)` | `origin.get(id)` のファイルから除き、`removedOrigin.put(id, slot)` |

- 書き込みの予約は、変わったファイルだけ `writer.request(slot.file, slot のスナップショット)` する。`DebouncedWriter` はもともとファイルごとに予約を持つ（`DebouncedWriter.java:109` の `Map<Path, List<Memo>> pending`）ので、2ファイルでもそのまま使える。保存の失敗・回復の通知もファイルごと（`MemoStore.java:59-72`）なので変えない
- なぜ `removedOrigin` が要るか: 元に戻すは削除の取り消しを `repo.add(edit.before())` で行う（`draw/DrawingController.java:141`）。元のファイルを覚えていないと、直下のメモを消して元に戻した時にメモ帳へ移ってしまう（決定事項 4 に反する）
- 上限 256 は、元に戻すの履歴の上限 100（`draw/UndoHistory.java:12`）より大きければよい。開き直し（`open`/`close`）で空にする

### 3.5 MemoRepository に足すもの（`store/MemoRepository.java`）

### 3.6 元に戻すの履歴（`draw/DrawingController.java`）

- **サーバーが変わったら履歴を捨てる**: 今は、ディメンションの実体が変わった時（`draw/MapCanvasRenderer.java:100-105`）と、ミニマップの同期が true を返した時（`jm/ScribbleBridge.java:724-725`）にしか捨てない。プロキシの中で同じディメンションのまま移ると履歴が残り、元に戻すが別のサーバーのメモ帳へ書く恐れがある
  - `DrawingController` に `private long historyGeneration` を持ち、`add`・`update`・`remove`・`undo`・`redo`・`canUndo`・`canRedo`（`:88-160`）の最初で `repo.generation() != historyGeneration` なら `history.clear()`・`stroke = null`・`historyGeneration = repo.generation()` にする（`ensureFresh(repo)` という private メソッド1つにまとめる）
  - `MapCanvasRenderer` の描画のキャッシュも、`dimension != lastDimension` に加えて `repo.generation()` が変わった時に `cache.clear()` する（`:100-105`）
- **移す操作の履歴**: `record Edit(Memo before, Memo after)`（`:32`）に加え、`record Move(List<UUID> ids, MoveDirection direction)` を足し、履歴の型を `sealed interface HistoryEntry permits Edit, Move` にする（`UndoHistory<T>` は型引数なので変更不要）
  - `undo()` で `Move` を取り出したら、`repo.move(ids, direction の逆, result -> ...)` を呼ぶ。`redo()` は同じ向き。結果が失敗なら履歴を元に戻す（`popUndo` で移した分を `push` し直す代わりに、`UndoHistory` に `undoPop` の取り消し用の `restoreUndo(T)` / `restoreRedo(T)` を足す）。失敗は `state.notice(...)` で知らせる
  - `undo()`・`redo()` は移す操作では「始めた」時点で true を返す（結果は非同期）
- `repo.isBusy()` の間は、`add`・`update`・`remove`・`undo`・`redo` を何もせずに返し、`state.notice(NOTICE_BUSY)`（新しい文言「移しています」。文言は Dev-UI-Designer）を出す

## 4. notebooks.json・フォルダ名・画面から呼ぶ API

### 4.1 形式

場所: `mapscribble/servers/<アドレス>/notebooks.json`。文字コード UTF-8、改行 `\n`、Gson で書く（`MemoFile` と同じ `com.google.gson`、`MemoFile.java:3-6`）。

```json
{
  "format": 1,
  "mode": "auto",
  "splitAt": "2026-11-17T12:34:56Z",
  "autoStopped": false,
  "notebooks": [
    {
      "id": "nb-1a2b3c4d5e6f7a8b",
      "name": "",
      "created": "2026-11-17T12:34:56Z",
      "origin": "seed"
    },
    {

      "name": "資源（リセット前）",

```

| キー | 型 | 意味 |
|---|---|---|
| `format` | int | 形式の版。**1 以外・無しなら UNSUPPORTED として読まず、上書きもしない**（`MemoFile` と同じ扱い） |
| `mode` | `"auto"` / `"user"` / `"off"` | `auto`: 同じ接続の中でハッシュの変化を見て記録した。`user`: 利用者が分けると入れた。`off`: 利用者が分けないと選んだ（自動の判定でも記録しない）。ファイルが無い＝未判定 |
| `splitAt` | ISO-8601（UTC） | 分けると記録した時刻 |
| `autoStopped` | bool | 2.6 の上限で自動の作成を止めた |
| `notebooks[].id` | string | フォルダ名そのもの。作ったら変えない |
| `notebooks[].name` | string | 表示用の名前（空なら画面が既定の表示を出す。既定の表示は Dev-UI-Designer） |
| `notebooks[].created` | ISO-8601 | 作った時刻 |
| `notebooks[].origin` | `"seed"` / `"manual"` / `"jm010"` | どう作られたか（ハッシュから自動・手で作った・0.1.0 の取り込み。7.2） |
| `bindings` | object | ハッシュ（16桁の小文字16進の文字列）→ メモ帳の id。1つのハッシュに1つのメモ帳 |

- ハッシュは JSON の数値にせず、**16桁の16進の文字列**にする（long を数値で書くと、他の道具で読んだ時に倍精度へ丸められる恐れがあるため）
- 読み込みの検査（1つでも外れたらその項目を捨てて warn。ファイル全体は捨てない。ただし `format` の違いはファイル全体を UNSUPPORTED）:
  - `id` は正規表現 `^nb-[0-9a-z][0-9a-z-]{0,39}$` に合うこと（**`..`・`/`・`\`・ドライブ名を通さない。フォルダの外へ書かせないための検査**）
  - `bindings` の鍵は `^[0-9a-f]{16}$`、値は `notebooks` にある id
  - `name` は 64 文字までに切り、制御文字（`\p{Cc}`）を除く
- 知らないキーは捨てずに持ち、書き戻す時に残す（`JsonObject` を持ち回る）。新しい版が足したキーを古い版が消さないため

### 4.2 読み書き（`store/NotebookFile`・`store/NotebookRegistry`、新規）

- `NotebookFile`（状態を持たない。`MemoFile` と同じ形）: `read(Path) → ReadResult(Status, Notebooks, detail)`、`toJson(Notebooks)`、書き込みは `MemoFile.writeAtomic` をそのまま使う（一時ファイル → ATOMIC_MOVE）
- `NotebookRegistry`（主スレッドから使う）: アドレスのフォルダ（`Path`）ごとに読んだ結果をメモリに持つ（`HashMap<Path, Entry>`）。読むのはそのアドレスで最初に必要になった時だけ（鍵が変わった時の経路でしか呼ばれない）
- **書き込みは書き込み用スレッドで行い、主スレッドは待たない**。`DebouncedWriter` に次を足す（`store/DebouncedWriter.java`）:
  ```java
  /** 書き込み用スレッドで、予約分を書き切った後に task を実行する。止めた後は呼び出したスレッドで実行する。 */
  public <T> CompletableFuture<T> submit(Callable<T> task);
  ```
  `notebooks.json` の書き込みは「`writeAtomic` → `NotebookFile.read` で読み直して内容が同じか」を1つの task にし、成功・失敗を主スレッドへ戻す（`Minecraft.getInstance().execute`。`StoreSession.java:43-47` と同じ戻し方）
- 読めない（CORRUPT・UNSUPPORTED）アドレスは、メモリ上で「分けない・書かない」に固定し、そのセッションでは読み直さない

### 4.3 フォルダ名の作り方

| 種類 | 作り方 | 例 |
|---|---|---|
| ハッシュから自動 | `"nb-" + String.format("%016x", hash)`（負の値も2の補数で16桁） | `nb-1a2b3c4d5e6f7a8b` |
| 手で作る | `"nb-m" + UTC の yyyyMMdd-HHmmss`。同じ名前が `notebooks` かフォルダにあれば末尾に `-2`、`-3`… | `nb-m20261118-090000` |
| 0.1.0 の取り込み（7.2） | `"nb-j" + JourneyMap のフォルダ名を [^0-9a-z] → `-` に置き換え、40文字に切ったもの`。重複は `-2`… | `nb-jexample-server-1a2b` |

- どれも 4.1 の正規表現に合う。Windows・Linux とも小文字だけなので大小文字の違いで衝突しない
- フォルダは、最初にメモを書く時に `MemoFile.writeAtomic` が作る（`MemoFile.java:165` の `Files.createDirectories`）。メモ帳を作っただけでは空のフォルダを作らない

### 4.4 メモ帳の決め方（`NotebookRegistry.resolve`）

`String resolve(Path addressDir, long seedHash, ManualSelection manual)` → メモ帳の id か null（直下）

1. `manual` があり、その接続・そのハッシュのものなら、その id（null＝直下を選んだ、も含む）
2. 記録が読めない・無い・`mode == off` → null
3. `seedHash == 0` → null
4. `bindings[hex]` があり、そのメモ帳が `notebooks` にある → その id
5. `autoStopped` → null
6. それ以外（分けているアドレスで新しいハッシュ）→ `nb-<hex>` を作って `bindings` に足す。2.5 の 6 と同じく**書いてから使う**: 書き込みが終わるまでは null（直下）を返し、書けたら主スレッドで鍵を作り直す。2.6 の上限もここで数える

### 4.5 画面から呼ぶ API（`store/NotebookAccess`、新規。実装は StoreSession）

保存先の画面（Dev-UI-Designer が設計、Dev-Engineer が実装）は、この型だけを使い、ファイルを知らない。呼び出しは主スレッドから。結果は主スレッドで返す。


## 5. 移す操作の手順

対象: 今のディメンションの、分ける前のファイル（legacy）から主ファイル（メモ帳）へ。逆向き（元に戻す）は向きを入れ替えた同じ手順で、`.before-split.bak` は作らない。

前提: メモ帳を開いていて、主ファイルも分ける前のファイルも書ける（`writable`）。そうでなければ `MoveResult.failed("mapscribble.move.unavailable")`。

主スレッド（`MemoStore.move`）:

1. `busy = true`、`notifyListeners()`（画面が「移しています」を出せるように）
2. 移すメモ `M` を決める: legacy の中で `ids` に含まれ、主ファイルに同じ id が無いもの。`M` が空なら `busy = false` で `ok` を返す
3. スナップショットを作る: `primaryBefore`、`primaryAfter = primaryBefore + M`（末尾に足す＝上に描かれる）、`legacyBefore`、`legacyAfter = legacyBefore − M`。`token = generation`
4. `writer.submit(task)` に渡す（書き込み用スレッド。`submit` は先に予約分を書き切るので、移す前の変更が全部ファイルに入った後で動く）

書き込み用スレッド（task）:

5. `MemoFile.writeAtomic(primary, toJson(primaryAfter))`
6. 主ファイルを読み直す: バイト列が書いた JSON と同じで、`MemoFile.parse` が OK で、`M` の id が全部あること。違えば `writeAtomic(primary, toJson(primaryBefore))` で戻して失敗
7. `.before-split.bak`: `legacy` と同じフォルダの `<ファイル名>.before-split.bak`（例 `minecraft__overworld.json.before-split.bak`）が**無い時だけ** `Files.copy(legacy, bak, COPY_ATTRIBUTES)`。あればそのまま（1回だけ）。コピーに失敗したら 6 と同じく主ファイルを戻して失敗
8. `MemoFile.writeAtomic(legacy, toJson(legacyAfter))`
9. 分ける前のファイルを読み直す: バイト列が書いた JSON と同じで、`M` の id が無いこと。違えば主ファイルを `primaryBefore` に戻して失敗（分ける前のファイルは atomic な置き換えなので、失敗した時は元の内容のまま）
10. 成功・失敗を返す

主スレッド（結果を受けた時）:

11. `generation != token`（途中で別のファイルへ切り替わった）なら、メモリは触らない（ファイルは書き終わっていて、次に開いた時に正しく読まれる）。`busy = false`
12. 成功: メモリ上の `primary.memos`・`legacy.memos`・`origin` を `After` に差し替え、`busy = false`、`refreshView()`、`notifyListeners()`、`onDone(ok)`
13. 失敗: メモリは触らない、`busy = false`、`problemHandler` に理由を知らせ、`onDone(failed)`

- 途中でゲームが落ちた時: 5〜8 のどこで落ちても、各ファイルは atomic な置き換えなので「書く前」か「書いた後」のどちらか。最悪でも「主ファイルにも分ける前のファイルにも同じメモがある」で、3.3 のとおり主ファイルの方だけが出る（重複して見えない・消えない）
- 「今見えている範囲だけ移す」（02章）は、画面が `ids` を渡すことで実現する（見えている範囲の計算は画面側）

### 6.2 予備: JVM の終了フック

- `StoreSession` の static 初期化で `Runtime.getRuntime().addShutdownHook(new Thread(StoreSession::shutdown, "MapScribble-Shutdown"))` を1回登録する（ローダーのイベントが呼ばれなかった時・1.18.2 等でイベントが無い時のため）
- `shutdown()` は `AtomicBoolean` で**1回だけ**働くようにする（イベントと終了フックの両方から呼ばれるため）。中身は今のまま `CONTROLLER.flush(); STORE.shutdown();`（`:109-112`）
- 止めた後に来た書き込みの予約は、`DebouncedWriter.request` が `RejectedExecutionException` を受けて呼んだスレッドで書く（`DebouncedWriter.java:130-134`）ので失われない
- `flush` は最大10秒待つ（`DebouncedWriter.java:147`）。終了の時だけなので許す
- 主スレッドで `Minecraft.execute` へ戻す処理（`StoreSession.java:43-47`）は、終了の途中では動かないことがある。保存の通知が出ないだけで、書き込み自体には影響しない

### 7.3 試験項目（`src/test/java/.../store/LegacyDataRegressionTest`、新規。以後の版は資料を足すだけ）

すべて「資料を一時フォルダへコピー → 0.4.0 のコードで開く → 確かめる」。

1. 0.2.0・0.3.0 の直下のファイルを、メモ帳を開いていない状態（`open(file)`）で読み、全部読める・件数と中身（`Memo` の equals）が資料と同じ
2. 同じファイルを、メモ帳を開いた状態（`open(notebookFile, legacyFile)`）で読み、分ける前のメモとして全部見える（`memos()` に全部あり、`isLegacy` が true）
3. 1・2 の後、何も編集せずに `close()` した時、元のファイルが**バイト単位で変わっていない**（`Files.mismatch == -1`）。`.tmp`・`.bak` が増えていない
4. 分ける前のメモを1件編集すると、**直下のファイル**が書き換わり、メモ帳のファイルは作られない。他のメモの内容は変わらない
5. 分ける前のメモを消して元に戻すと、直下のファイルに戻る（メモ帳へ移らない。3.4）
6. 移す操作: メモ帳へ書いて読み直してから元から除く。`.before-split.bak` が元の内容とバイト単位で同じ。2回目に移しても `.bak` が上書きされない。元に戻すで、両方のファイルが移す前とバイト単位で同じ（`.bak` は残る）
7. 移す途中で失敗させる（試験用の `DebouncedWriter.Sink` で、分ける前のファイルへの書き込みを失敗させる）と、主ファイルが元に戻り、分ける前のファイルは元のまま
8. 壊れた JSON・`format` 2 のファイル: 読まない・上書きしない（バイト単位で変わらない）・知らせが出る。分ける前のファイルが壊れている時は、主ファイルだけ使える
9. 0.1.0 の資料（W0）: 候補が1つなら直下へコピーされ、元の JourneyMap のフォルダのファイルはバイト単位で変わらない。直下に同じ名前があればコピーしない。候補が2つなら（9.3 の決定どおりに）取り込まれる。2回目の呼び出しでは何もしない
10. 0.2.0 の旧引き継ぎ（`journeymap/addon-data/mapscribble/`）: 今と同じく、直下に無い時だけコピーされる
11. `notebooks.json`: 書いて読み直すと同じ。`format` 2 は読まず上書きしない。知らないキーが書き戻しで残る。`id` に `../x`・`nb-A`・`C:` を入れたものは捨てられる
12. `SplitDetector`: 同じ接続・同じディメンションIDでハッシュが変わったら split。別のディメンションIDなら split しない（Multiverse 型）。0 を挟んでも比べられる。接続が変わったら表が空になる。lobby(overworld)→survival(nether)→survival(overworld) で split
13. `NotebookRegistry.resolve`: 2.4・4.4 の順のとおり。`autoStopped` の上限
14. 古い版へ戻した時の確認（試験で見られる範囲）: 0.4.0 で分けた後の直下のファイルが、0.3.0 の `MemoFile.read`（＝今の `MemoFile.read`。同一）で読める。`notebooks.json` やメモ帳のフォルダがあっても直下の読み込みに影響しない

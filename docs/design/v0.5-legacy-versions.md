## 1. 03 章で未確認だった 4 点

確認の手段: Mojang の公開マッピング（`client.txt`、piston-data から取得）でクラス・メンバーを 1.18.2 / 1.19.2 / 1.20.1 で比べ、可視性はクライアント jar を `javap` で見た（難読化名で引く）。Forge は universal / fmlcore / javafmllanguage / MDK の jar、Fabric API はモジュールの jar を `javap` で見た。

### 1.1 MultiLineEditBox

| 版 | 有無 | 根拠 |
|---|---|---|
| 1.19.2 | ある | `client.txt` の `net.minecraft.client.gui.components.MultiLineEditBox -> eib` |
| 1.18.2 | **無い** | `client.txt` に `MultiLineEditBox`・`MultilineTextField`・`AbstractScrollWidget` のどれも無い |

1.19.2 の MultiLineEditBox は、今の 1.20.1 枝（`ui/NoteEditScreen.java:98`）と同じ 7 引数のコンストラクタ `(Font, int, int, int, int, Component, Component)` を持ち、`setCharacterLimit`・`setValueListener`・`setValue`・`getValue` もある。違いはナレーションのメソッド名（1.19.2 は `updateNarration`、1.20.1 は `updateWidgetNarration`）と描画の引数（`PoseStack`）だけで、NoteEditScreen は自分でナレーションを上書きしていないので影響は描画の型だけ。

1.18.2 で使える材料: `net.minecraft.client.gui.font.TextFieldHelper`（コンストラクタ `(Supplier, Consumer, Supplier, Consumer, Predicate)`、`insertText`・`moveByChars`・選択・コピー・貼り付けを持つ）、`StringSplitter`（折り返し位置の計算）、`BookEditScreen`（本の編集画面。この 2 つで複数行入力を作っている手本）。

### 1.2 1.18.2 Forge の RegisterKeyMappingsEvent

| 版 | 方法 |
|---|---|
| Forge 43.5.0（1.19.2） | `net.minecraftforge.client.event.RegisterKeyMappingsEvent`（`IModBusEvent`、`register(KeyMapping)`）。1.20.1 枝と同じ |
| Forge 40.3.0（1.18.2） | イベントは**無い**。`net.minecraftforge.client.ClientRegistry.registerKeyBinding(KeyMapping)`（`public static synchronized`）を `FMLClientSetupEvent` の中で呼ぶ |

### 1.3 RegisterGuiOverlaysEvent

| 版 | 方法 |
|---|---|
| Forge 43.5.0（1.19.2） | ある。`registerAbove(ResourceLocation, String, IGuiOverlay)`、`VanillaGuiOverlay.SLEEP_FADE.id()` もある。ただし `IGuiOverlay.render(ForgeGui, PoseStack, float, int, int)` で、描画の引数が `PoseStack` |
| Forge 40.3.0（1.18.2） | **無い**。`net.minecraftforge.client.gui.OverlayRegistry.registerOverlayAbove(IIngameOverlay, String, IIngameOverlay)` に `ForgeIngameGui.SLEEP_FADE_ELEMENT` を渡す。`IIngameOverlay.render(ForgeIngameGui, PoseStack, float, int, int)` |

1.18.2 の代わりの案として `RenderGameOverlayEvent.Post`（`getMatrixStack()`、`getType()` で `ElementType.ALL` を見る）もあるが、描く順（睡眠の暗転の上）を 1.19.2 以降と揃えられるのは `OverlayRegistry` の方なので、そちらを推す。

### 1.4 pack_format

バニラの `version.json` の値: 1.19.2 は `resource 9, data 10`、1.18.2 は `resource 8, data 9`。

Forge 構成の jar に入れる `pack.mcmeta` の値（`versions/<構成>/gradle.properties` の `pack_mcmeta_fields`）の候補:

| 候補 | 1.19.2 | 1.18.2 |
|---|---|---|
| A. Forge 自身の jar（universal）の pack.mcmeta | `"pack_format": 8, "forge:resource_pack_format": 9, "forge:data_pack_format": 10` | `"pack_format": 8, "forge:resource_pack_format": 8, "forge:data_pack_format": 9` |
| B. Forge の MDK の pack.mcmeta | `"pack_format": 9, "forge:resource_pack_format": 9, "forge:data_pack_format": 10` | `"pack_format": 9, "forge:resource_pack_format": 8, "forge:data_pack_format": 9` |

- **推奨は A。** 既存の方針が「Forge 自身の jar と同じ値を置く」（`stonecutter.gradle.kts:33`、`versions/1.20.1-forge/gradle.properties:12`）であり、同じ値で Forge 自身が読み込まれている実例がある
- B を採らない理由: `forge:` の 2 項目は A と同じで、違うのは `pack_format` だけ。Forge 1.18〜1.19 は `forge:` の項目があればそちらで互換を判定する作りと理解しているが**手元では確かめていない**。差が出ないなら、既存の方針から外れる理由が無い
- `generatePackMcmeta`（`stonecutter.gradle.kts:34-43`）は値の文字列をそのまま `"pack"` の中に差し込むので、カンマで区切った 3 項目をそのまま書ける

## 2. Minecraft 本体の API の差（1.18.2 / 1.19.2 と 1.20.1）

`client.txt` で比べた結果。左が今のコードが使っている 1.20.1 の形。

| 今の形（1.20.1） | 1.19.2 | 1.18.2 |
|---|---|---|
| `GuiGraphics` | 無い（1.20 から）。`PoseStack` と `GuiComponent` の静的メソッド | 同左 |

| `AbstractWidget#isHovered()` | 無い。protected フィールド `isHovered`（public は `isHoveredOrFocused()`） | 同左 |

| `Screen#setInitialFocus` | 無い。`setFocused(GuiEventListener)` と部品側の `changeFocus(true)` | 同左 |
| `AbstractWidget#setFocused(boolean)` | **protected**（javap: `ehn.d(boolean)`） | **protected**（`eac.d(boolean)`） |
| `renderBackground(GuiGraphics)` | `renderBackground(PoseStack)` | 同左 |
| `CycleButton.builder(fn).withValues(T[]).withInitialValue(v).create(...)` | 同じ（配列版 `withValues(Object[])` がある） | 同じ（配列版がある） |

## 4. 描画の窓口（Gfx）の古い枝

`compat/Gfx.java:28-70` は今 `GuiGraphicsExtractor`（26.1 以降）と `GuiGraphics`（それ以前）の 2 枝。ここへ `//? if <1.20` の枝を足し、`PoseStack` を包む。`raw()` が `PoseStack` を返すので、`NoteEditScreen` の `super.renderBackground(g.raw())`・`parent.render(g.raw(), ...)`（`ui/NoteEditScreen.java:295-318`）は同じ形で通る。

`compat/GuiCompat.java` の描画系に要る古い枝:

| メソッド（`GuiCompat`） | 1.19.2 | 1.18.2 | 注意 |
|---|---|---|---|
| `pushPose/popPose/translate2D/scale2D` | `PoseStack` の同名メソッド | 同左 | |
| `rotate2D` | `Vector3f.ZP.rotationDegrees` | 同左 | |
| `enableScissor/disableScissor` | `GuiComponent.enableScissor/disableScissor` | `RenderSystem.enableScissor` へ換算: `x = minX*scale`、`y = windowHeight - maxY*scale`、`w = (maxX-minX)*scale`、`h = (maxY-minY)*scale` | 入れ子はできない。呼び出しは `map/MinimapHudRenderer.java:100` の 1 か所で入れ子にしていない |
| `fill`（z 付き） | `translate(0, 0, z)` で包んで `GuiComponent.fill` | 同左 | |
| `outline` | `fill` 4 本 | 同左 | |
| `text/centeredText`（`shadow`） | 影ありは `GuiComponent.drawString`、影なしは `Font.draw` | 同左 | 中央寄せは `font.width(text)` から自分で計算 |
| `blitIcon`（色付き） | `setShaderTexture(0, rl)` → `setShaderColor` → `GuiComponent.blit(pose, x, y, 0f, 0f, size, size, size, size)` → 色を戻す | 同左 | |
| `drawTooltip` | `Minecraft.getInstance().screen` の `renderComponentTooltip(pose, lines, x, y)` | 同左 | 下記 |
| `nextLayer` | 何もしない（1.20.1 枝と同じ） | 同左 | |

**tooltip の方式の候補**

| 案 | 内容 | 判断 |
|---|---|---|
| **A. 表示中の画面から呼ぶ（推奨）** | `drawTooltip` の中で `Minecraft.getInstance().screen` を取り、null なら描かない | 呼び出し元 4 か所（`map/ScreenMapHost.java:380`・`:392`、`ui/ScribbleUi.java:126`、`ui/ToolBand.java:344`）はどれも画面の上で、HUD からは呼んでいない。`renderComponentTooltip` は public なので、地図 MOD の画面でも呼べる。引数を増やさずに済む |
| B. `Gfx` に `Screen` を持たせる | `Gfx.of(PoseStack, Screen)` | HUD の入口では Screen が無く、全入口で渡し方を決める必要がある。A で足りる以上、窓口の形を広げる理由が無い |

### 7.5 ラッパーの組み立て（rules/29 に沿う形）

**非公開のメンバーへの入口 — 方式の候補**

| 案 | 内容 | 判断 |
|---|---|---|
| **A. Mixin の `@Accessor`（推奨）** | Xaero の `GuiMap` と JourneyMap の `Fullscreen` に Accessor のインターフェースを当てる（`gridRenderer` は static なので static の Accessor） | rules/29 :29・:48 が認める手段。型付きで、コンパイル時に名前の誤りが分かる |
| B. Access Widener（Fabric）/ Access Transformer（Forge） | | Minecraft 本体のクラスが対象の仕組みで、他の MOD のクラスには使えない。不可 |
| C. 公開 API だけで書く | | JourneyMap は中心の精度が落ちドラッグを止められず、Xaero は位置を動かせない（7.2）。機能が欠ける。採らない |
| D. 03 章の案（リフレクションの探索に名前を足す） | | rules/29 違反（:21・:40）。採らない |
| E. 古い版では地図 MOD との連携を外す | | 利用者が使える機能が版で欠ける。採らない |

Mixin はこのリポジトリでまだ使っていない（`org.spongepowered` も mixin 設定も無い）。入れる時に要るもの:

- Fabric: `fabric.mod.json` の `"mixins"`。refmap は Loom が作る
- legacyforge（1.18.2・1.19.2・1.20.1 の Forge）: 文書（ModDevGradle の `LEGACY.md`）のとおり、Mixin の注釈処理器・refmap の生成と、jar の manifest の `MixinConfigs`。無いと製品の jar で Mixin が読まれない
- 地図 MOD が入っていない時に Mixin を当てに行かないよう、Mixin の設定に適用判定のプラグイン（`IMixinConfigPlugin#shouldApplyMixin`）を置き、ローダーの公開 API（Fabric: `FabricLoader.getInstance().isModLoaded`、Forge: 読み込み済みの MOD の一覧）で判定する。`Class.forName` で調べない（rules/29 :23・:41）。Mixin の設定は `"required": false` にする
- 既存の 21 構成にも Mixin を入れる場合、NeoForge は `neoforge.mods.toml` の `[[mixins]]`、ForgeGradle 7 の構成の配線は**未調査**

**実装の選び分け**

| 案 | 内容 | 判断 |
|---|---|---|
| **A. Stonecutter の `//?` で import・型を構成ごとに切り替え、MOD の有無はローダーの公開 API で見る（推奨）** | 各構成でコンパイルする地図 MOD の版は 1 つなので、型の違い（FTB の `client.LargeMapScreen` と `client.gui.LargeMapScreen` 等）は `//?` で吸収できる。地図 MOD の型を参照する実装クラスは、`isModLoaded` が真の時だけ作り、参照を別クラスに隔離して、MOD が無い時にクラスが読み込まれないようにする | 今の版分岐の仕組みと同じで、仕組みが増えない。rules/29 :49 の「公開 API の値で実装を選ぶ」に当たる |
| B. 地図 MOD ごと・版ごとに別のソースセット（またはモジュール）を作る | | Stonecutter が既に版ごとのソースを作っており、仕組みが二重になる。採らない |
| C. クラス名の文字列で比べる・`Class.forName` で有無を見る（今の形） | | rules/29 違反。採らない |

**地図 MOD の版の幅**: 型付きにすると、コンパイルした版と違う版の地図 MOD（例: 古い Xaero's Minimap で `getHudConfigs` が無いもの）では `NoSuchMethodError` になる。対応する版の下限を決め、それより古い版では連携を有効にしない（ローダーの公開 API で地図 MOD の版を読んで判定する）か、`fabric.mod.json` の `breaks`・`mods.toml` の任意の依存の `versionRange` で宣言する。下限の値は**未決**（Xaero's Minimap で `getHudConfigs` が入った版は未調査）。

**既存の 21 構成への波及**: rules/29 :36 は「改修する箇所にリフレクションがあれば、その改修の中でラッパーへ置き換える」。adapter は全構成で 1 つのソースなので、0.5.0 で adapter を直すと**既存の 21 構成の地図 MOD 連携も型付きに置き換えることになる**。そのためには既存の構成ごとの地図 MOD の版・座標・クラス名（FTB の 26.1 以降の `client.gui.map.LargeMapScreen`・`client.gui.widget.ScreenWrapper` など）の調査が別に要る。この調査はこのメモの範囲外で、まだ行っていない。

**改修の対象外で、リフレクションが残っている所**（rules/29 :36 に従い事実だけ記す）: `jm/MapProjection.java`（`getMethod` 1 件）、`jm/ScribbleBridge.java`（`getDeclaredField`・`setAccessible` の 3 件）、`src/gametest` の 7 ファイル。`jm/` は古い 4 構成ではコンパイルされない。

## 12. 根拠の取り方（再現の手順）

- Minecraft 本体: `https://piston-meta.mojang.com/mc/game/version_manifest_v2.json` → 各版の JSON の `downloads.client_mappings`（`client.txt`）と `downloads.client`（jar）。`client.txt` でクラスの Mojang 名と難読化名を引き、jar を `javap -p <難読化名>` して可視性を見る
- Forge: `https://maven.minecraftforge.net/net/minecraftforge/forge/<版>/` の `-universal.jar`・`-mdk.zip`、fmlcore・javafmllanguage は `net/minecraftforge/fmlcore/<版>/`・`net/minecraftforge/javafmllanguage/<版>/`。推奨版は `https://files.minecraftforge.net/net/minecraftforge/forge/promotions_slim.json`
- Fabric API: `https://maven.fabricmc.net/net/fabricmc/fabric-api/` の各モジュールの jar
- 地図 MOD: Modrinth の API `https://api.modrinth.com/v2/project/<slug>/version?game_versions=[...]&loaders=[...]`、FTB は `https://maven.ftb.dev/releases/dev/ftb/mods/<名前>/maven-metadata.xml`
- ModDevGradle（legacyforge）の対応範囲: `https://github.com/neoforged/ModDevGradle/blob/main/LEGACY.md`
- Loom の plugin ID: `https://docs.fabricmc.net/develop/loom/`

### 13.1 (a) 地図 MOD のラッパー化は、0.5.0 で全 25 構成に対して行う

### 13.2 (b) Mixin を入れる

**結論**: 入れる。対象は**地図 MOD のクラスの非公開メンバーだけ**とし、Minecraft 本体の非公開メンバーは今までどおり Access Widener / Access Transformer で開ける。

**根拠**
- rules/29 :29「MOD で非公開のメンバーが要る時: Mixin の `@Accessor` / `@Invoker`、Access Widener（Fabric）、Access Transformer（Forge / NeoForge）で型付きの入口を作る」、:48「Mixin・Access Widener・Access Transformer で型付きの入口を作ること」は禁止されない
- Access Widener / Access Transformer は Minecraft 本体を対象にする仕組みで、他の MOD のクラスには効かない（7.5 の B）。地図 MOD の private のフィールドに型付きで触れる手段は Mixin しかない
- 公開 API だけでは機能が欠ける（JourneyMap の中心の精度とドラッグの停止、Xaero's World Map の位置の変更。7.2）

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| 公開 API だけで書く | 7.2 のとおり機能が欠ける（線が数十ピクセルずれる、地図を動かせない） |
| Mixin の `@Inject` で地図 MOD の処理に割り込み、値を横取りする | 欲しいのはフィールドの読み書きだけで、処理に割り込むと地図 MOD の更新に弱くなる。Accessor の方が当てる面が小さい |
| Minecraft 本体のメンバー（`Screen.renderables`）も Mixin の Accessor で開ける | 既に Access Widener / Access Transformer の 4 ファイルがあり、同じ種類のものを 2 つの仕組みに分ける理由が無い |

#### 13.2.4 Mixin の設定と適用判定

- 設定ファイルは**形のソースセットごとに 1 つ**: `mapscribble.jm5.mixins.json`、`mapscribble.xwm.mixins.json`（`GuiMapAccessor` と `GuiMapDimensionAccessor`）、`mapscribble.xmm.mixins.json`（1.21.11 と 26.x の枝だけ中身がある。中身が空の構成では設定を登録しない）、`mapscribble.ftb.mixins.json`（`mapFtbChunks` の `LargeMapScreen`・`RegionMapPanel` の Accessor）。`mapXaeroMinimapLegacy` と `mapFtbChunksLegacy` は Mixin を使わないので設定を作らない。置き場所は各ソースセットの `resources`
- どの設定も `"required": false`、`"compatibilityLevel": "JAVA_17"`、`"plugin": "io.github.radishsprouts.mapscribble.map.api.MapMixinPlugin"`、`"client"` に Accessor を並べる
- `MapMixinPlugin`（`mapapi` に置く。13.5）は `onLoad(mixinPackage)` で自分がどの形かを決め、`shouldApplyMixin` で `MapGate.allowed(形)`（13.4.5）を返す。`GuiMapDimensionAccessor` だけは、それに加えて版が `map_xwm_dim_min` 以上か（行が無い構成では常に真）を見て、結果を `MapGate` に覚えさせる（13.2.1）。**`Class.forName` でクラスの有無を見ない**（rules/29 :23・:41）
- ローダーの版の情報がまだ読めない時（Forge の読み込み済みの一覧が `null` 等）は `true` を返す。地図 MOD が無ければ `required: false` なので Mixin は警告を出して飛ばし、ゲームは止まらない。連携を有効にするかは、後で main が `MapGate` でもう一度決める。`GuiMapDimensionAccessor` を版が読めないまま当てた時も、フィールドが無ければ当たらないだけなので、View は「当てたか」の旗が真でも `LinkageError`・`ClassCastException` を捕まえて次元だけを null にする（連携ごと止めない）

### 13.4 (c) 地図 MOD ごとの対応版の下限の決め方

**結論**
1. **下限は、0.4.0 のリフレクションの経路が動いていた範囲より狭めない。** 構成ごと・地図 MOD ごとに、0.4.0 の adapter が必要としたメンバーが全部そろう最古の版を下限にする（プラン 01 章 :74「見えなくしない。更新の前に見えていたメモは、更新の後も同じ場面で見える」。下限を上げると、古い地図 MOD を使っている利用者のメモが 0.5.0 で見えなくなる）
2. その範囲の中に API の形が複数あれば、形ごとに実装とソースセットを作り、両方を同じ jar に入れる（13.5）
3. **上限は置かない。** 地図 MOD が新しい版で名前を変えた時は、型付きの呼び出しが投げる `LinkageError`（`NoSuchMethodError`・`NoSuchFieldError`・`AbstractMethodError`・`IncompatibleClassChangeError`）と `ClassCastException` を捕まえて、その連携だけを無効にする（二段目の守り。今の adapter の `catch` と同じ振る舞い）
4. 範囲の外の版では、その連携だけを無効にし、ログに 1 行出す。ゲームの起動は止めない

**根拠**
- rules/29 :49「公開 API の値（サーバー名・版）で実装を選ぶこと」は禁止されない。版はローダーの公開 API で読む（13.4.2）
- 0.4.0 の利用者の環境を 0.5.0 で狭めないことは、プラン 01 章の「過去のデータを消さない」の 2 項（見えなくしない）から来る

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| `fabric.mod.json` の `breaks`・`mods.toml` の任意の依存の `versionRange` で宣言する（7.5 の案） | 範囲の外の地図 MOD を入れている利用者は、**ゲームを起動できなくなる**。地図 MOD の連携は MapScribble の一部の機能で、起動を止めるほどの理由にならない |
| 各構成の「最新の地図 MOD」だけを下限にする | 0.4.0 で動いていた古い地図 MOD の利用者が、0.5.0 でメモを見られなくなる（01 章 :74 違反） |
| 上限も置く | 地図 MOD の新しい版が出るたびに MapScribble を出し直さないと連携が止まる。名前が変わっていなければ動き続けるべきで、変わった時は二段目の守りで安全に止まる |
| 版を見ず、`LinkageError` を捕まえるだけにする | Mixin の Accessor は当てた時点で失敗し得るので、当てる前に判定が要る。毎回の失敗をログに出すのも避けたい |

- 判定: `ModVersions` で版を読む → 読めなければ「入っていない」→ `VersionCompare` で `MapModRanges` の範囲（下限以上、上端があれば上端未満）と比べる → 範囲の中なら有効
- 範囲の外なら、ログに 1 行だけ出す（例: `[MapScribble] Xaero's Minimap 24.5.1 は連携の対象外です（24.6.1 以上で連携します）`）。画面の文言ではないので翻訳は要らない
- **`VersionCompare`** は純粋な関数にして、単体試験を付ける。仕様:
  - 版の文字列を `-`・`+`・`_` で区切る。**数字で始まる区切りのうち最後のもの**の、先頭の「数字とドットの並び」を本体の版とする（JourneyMap 6 の `26.3-6.0.10` → `6.0.10`、`1.21-6.0.0-beta.19` → `6.0.0`、`26.1-6.0.0-beta.65` → `6.0.0`、FTB の `1902.4.7-build.420` → `1902.4.7`、`26.1.2.11` → `26.1.2.11`、Xaero の `25.0.0` → `25.0.0`、JourneyMap 5 の `5.10.0` → `5.10.0`、`5.9.0beta2` → `5.9.0`）。`beta.19` は数字で始まらないので候補にならない
  - 先行版の印は、本体の版を取った区切りの残り（`5.9.0beta2` の `beta2`）か、その直後の区切り（`beta.19`）。これが `alpha`・`beta`・`pre`・`rc` で始まれば先行版として扱い、`alpha` < `beta` < `pre` < `rc` < 正式版、同じ種類は後ろの数で比べる（`6.0.0-beta.46`、`5.9.0beta2`）。`build.<数>` は比べない
  - 数字の段は左から数として比べ、足りない段は 0 とする
  - 入力は、ローダーが返す jar の中の版の文字列だけとする（Modrinth の `version_number` は入力にしない）。`MapModRanges` の下限・上端も同じ形で書く（13.4.3）
  - 試験には実在の文字列をそのまま使う。上の例に加え、13.4.6 (6) の `1.21-6.0.0-beta.19`、`26.1-6.0.0-beta.65`、`1.20.1-6.0.0-beta.1`、`5.9.0beta2`、`1802.3.5-build.128` を必ず含める（`1.20.1-6.0.0-beta.1` が `6.0.0-beta.46` より小さく比べられること、`5.9.0beta2` が `5.9.0` より小さく `5.8.4` より大きいことも確かめる）

### 13.5 ソースセットの構成

```
mapapi（Minecraft とローダーに依存。地図 MOD には依存しない）
  ├ map/api/*View         … 地図 MOD ごとの「生の値を読む・書く」インターフェース
  ├ map/api/ModVersions   … 13.4.2
  ├ map/api/VersionCompare、MapGate、MapModRanges（生成）、MapMixinPlugin、MapLog
  ▲
  │ 依存
mapJourneymap5 / mapXaeroWorldmap / mapXaeroMinimap / mapXaeroMinimapLegacy / mapFtbChunks / mapFtbChunksLegacy（形ごと。その構成に行がある形だけ作る）
  ├ View の実装（地図 MOD の型を型付きで呼ぶ）
  ├ Mixin の Accessor と設定（Mixin を使う形だけ。13.2.4）
  └ *Entry（隔離用の入口。create() が View を返す）
  ▲
  │ 依存
main（今のソース）
  ├ map/XaeroMapAdapter 等（今の adapter。View を受け取り、投影の計算とログは今のまま main に残す）
  ├ map/MapIntegrations（MapGate を通った形だけ、*Entry.create() を呼んで adapter を作る）
  └ map/GuardedMapAdapter（LinkageError・ClassCastException を捕まえて、その連携を無効にする）
```

- **View は地図 MOD の生の値だけを扱う**（例: `XaeroWorldMapView` は `handles(Screen)`、`cameraX/Z`、`scale`、`dimension()`〈次元の Accessor を当てていなければ null。13.2.1〉、`setCamera(x, z)`、`clearMouseDown()`）。`Projection` への換算・物理ピクセルの計算（例: `map/ftb/FtbChunksAdapter.java:174-176`）は main の adapter に残す。こうすると `geom/` を動かさずに済み、今の単体試験もそのまま使える。`mapapi` は main に依存しない
- `handles(Screen)` は形のソースセットの中で `instanceof GuiMap` 等の型付きの判定にする。FTB は `ScreenWrapper#getGui()` を型付きで呼んで `instanceof LargeMapScreen`（古い形と新しい形で `ScreenWrapper`・`LargeMapScreen` のパッケージが違う。13.4.6 (4)）
- FTB の 2 つの形は同じ `FtbLargeMapView` を実装する。1.20.1 では両方の形が同じ jar に入り、`MapGate` が版で片方だけを選ぶ
- **隔離**: main は `MapGate.allowed(形)` が真の時だけ `XaeroWorldMapEntry.create()` を呼ぶ。`*Entry` の戻りの型は `mapapi` の View なので、地図 MOD が入っていない時に地図 MOD のクラスは読み込まれない。main の該当の行は Stonecutter の定数（13.4.3）の `//? if map_xwm {` で囲み、形の無い構成ではコンパイルされない
- `JourneyMapLegacyAdapter` の `ScreenMapHost.hasPrimaryBridge()`（`:99`）による譲り合いは、main 同士の呼び出しなのでそのまま残す
- 今の `ScreenMapHost` の `static { ADAPTERS.add(new XaeroMapAdapter()); ... }`（`map/ScreenMapHost.java:106-110`）は `MapIntegrations.adapters()` に替える。並び（Xaero、FTB、JourneyMap 5）は変えない。`map/MinimapHudRenderer.java:33` の `SOURCE = new XaeroMinimapSource()` も `MapIntegrations.minimapSource()` に替える
- ログの受け口: `mapapi` の `MapLog` が `LoggerFactory.getLogger("mapscribble")`（今の `MapScribble.java:92` と同じ slf4j）を持つ
- ローダーのパッケージは全ソースセットで `io.github.radishsprouts.mapscribble` の下に置き、全部を 1 つの jar に入れる（`jar { from(sourceSets[...].output) }`。Loom の `remapJar`・legacyforge の reobf はこの jar を入力にする）。試験のソースセット（`src/test`・`src/gametest`）のクラスパスにも `mapapi` を足す
- Stonecutter が追加のソースセットの `//?` を処理することは、gametest の `//? if >=26.2`（`ScreenshotClientGameTest.java:86`・`:432`）が CI の 26.2・26.3 で動いていることから間接に分かる。新しいソースセットで直接確かめるのは U1（13.13）

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| 1 つの main に全部の形の jar を並べてコンパイルする | 同じ名前のクラス（`xaero.common.HudMod` 等）が衝突し、どちらの形にコンパイルされるか決まらない |
| `ServiceLoader` で実装を見つける | 見つけた実装を全部作ってしまい、地図 MOD が無い時もクラスが読まれる。実装の選び分けを実行時の探索に任せる形で、rules/29 :23 の趣旨に近い |
| Fabric のエントリポイント・Forge の `@EventBusSubscriber` で形ごとに登録する | ローダーごとの接着が形の数だけ増え、Forge・NeoForge・Fabric の 3 通りを書くことになる |
| `geom/` ごと `mapapi` へ移し、View ではなく `MapAdapter` を形のソースセットで実装する | 移すクラスが `geom/` の他のクラス（`Projection` → `Rect`、`MinimapGeometry` → `ClipRegion`・`ViewTransform`）を連れて行き、今の試験の置き場所も変わる。View に分けると移すものが無い |

### 13.6 3.1 文字の部品（Component）— `compat/Texts.java` に確定

**結論**: 3.1 の案 A。`compat/Texts.java` を新しく作り、`tr(String key, Object... args)`・`lit(String s)`・`empty()` の 3 つを置く。どれも `MutableComponent` を返す。1.18.2 の枝だけ `new TranslatableComponent(key, args)`・`new TextComponent(s)`・`new TextComponent("")` を返す（`TextComponent.EMPTY` は変更できない `Component` なので、`append` する呼び出し元のために `new TextComponent("")` にする）。13.0 の 9 ファイル・約 127 か所を呼び替える。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| 各所に `//?` を書く | 同じ違いが約 127 回書かれ、画面のコードが読めなくなる |

### 13.7 ボタン・tooltip・部品の基底

### 13.12 過去のデータ（プラン 01 章「過去のデータを消さない」）

- **メモのファイルの形式・場所・名前は変えない**（`store/` は `MemoStore` の試験用の入口を足すだけ）。`FORMAT` も上げない
- **ディメンションの値を変えない**: 型付きにした後も、各 adapter の `currentDimension(Screen)` は今と同じ型の値（`ResourceKey<Level>`）を返す。値の型が変わると、メモの振り分けが変わって見えなくなる（01 章 :74）。U8a〜U8d の完了の条件に含める
- **投影の値を変えない**: main に残した換算式（例: `map/ftb/FtbChunksAdapter.java:174-176`）は式を変えずに View の値を入れる。変えると描いた線の位置がずれ、利用者には別の場所のメモに見える
- 下限を 0.4.0 の範囲より上げない（13.4）
- 回帰試験（01 章 :79）は 0.4.0 の形の資料をそのまま使い、古い 4 構成でも回す（統合後の `test` に含まれる）
- 1.18.2・1.19.2 は 0.5.0 が最初の版なので、その構成での過去のデータは無い。既存の 21 構成の保存のしかたは変わらない
